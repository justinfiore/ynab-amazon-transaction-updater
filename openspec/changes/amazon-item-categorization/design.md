## Recommendation and status

Extract a shared item-classification service first, preserving Walmart behavior; then add opt-in Amazon item allocation with no default category and an independent shortlist. This is a proposal, not an implemented or financially qualified feature. The first-release payment scope and same-category itemization policy below are confirmed by the user.

## Current behavior and evidence

Inspected repository sources:

- `service/WalmartRemoteClassifier.groovy` accepts `WalmartOrderItem` but sends only titles and category choices. It owns both provider wire contracts, complete distribution validation, abstention, acceptance gates, bounds and metrics. Its fingerprint calls `WalmartEnrichment`; its policy is `walmart-choice-v1`; key access uses `WalmartProviderKeys`.
- `service/WalmartEnrichment.groovy` owns approved mappings, pooled inference/cache resolution, learning, plan fingerprints and journaled fresh-read/write recovery. Mapping keys currently use plan/product; that is safe only within the Walmart-specific store. Failures and abstentions are distinct: an inference failure can stop purchase allocation, while a valid abstention can become an uncategorized exception.
- `service/WalmartAllocation.groovy` mixes reusable catalog validation/payload mechanics with Walmart-only accounting. The default absorbs taxes, fees, tips and separate discounts; exceptions retain gross item amounts and fill descending-capacity charges. Reusing this planner unchanged would invent an Amazon default and misallocate costs.
- `service/WalmartOnboarding.groovy` assumes a `walmart` YAML section and mandatory default selection. `YNABService` exposes general plan/category/account/transaction operations under Walmart names. `WalmartJournal` supplies protected atomic state/locking but its stored financial plans are Walmart-specific.
- `model/AmazonOrder.groovy` has order total, date and item title/ASIN/unit price/quantity, but no currency/completeness, final payment ledger or explicit tax/discount/shipping fields. Missing totals/prices can read as zero; a value alone is not evidence of completeness.
- `service/PythonAmazonOrderFetcher.groovy` and `scripts/amazon_orders_bridge.py` pass grand total, payment metadata and item fields, not a complete settled ledger or adjustment breakdown. `AmazonService` adds CSV records, constructing totals from item prices. Email, CSV and Python evidence must be qualified separately; none is declared split-capable merely because it returns an order.
- `TransactionMatcher.findBestMatch` picks per transaction by score with a one-cent tolerance and no global order-consumption rule. `generateProposedMemo` summarizes up to three titles but sanitizes away URL punctuation and truncates the whole string. Neither behavior is suitable as financial allocation authority.
- `TransactionProcessor` only updates Amazon memos and stores processed IDs. Both it and the matcher skip transactions using memo-content/length heuristics. The updater filters Amazon candidates through this legacy path, unlike Walmart. This would prevent memo-only-to-categorization progression unless completion ownership changes.
- `EmailAmazonOrderFetcher.parseRefundFromEmail` retains a single extracted title and sets its price to the entire refund amount, falling back to refund subtotal when total is absent. `fetchOrders` merges records by `RETURN-<original order ID>`. Those legacy display records do not establish per-item refund amounts or preserve separate refund events; both need enhanced evidence handling for this proposal.

The active OpenSpec schema is `spec-driven`. Existing changes use `proposal.md`, `design.md`, unchecked implementation tasks and capability delta specs with `ADDED`/`MODIFIED Requirements` and `WHEN`/`THEN` scenarios. Existing canonical specs cover Amazon fetching and Walmart enrichment, not Amazon category writes.

### Pinned library evidence is richer than the current bridge

Source and offline-fixture investigation of the hash-verified `amazon-orders==6.0.0` wheel and upstream tag `6.0.0` found existing `subtotal`, `shipping_total`, `free_shipping`, promotion/coupon/subscription/multibuy/Amazon discounts, `estimated_tax`, `total_before_tax`, `gift_wrap`, gift-card/reward amounts and `refund_total`. Our bridge already requests full details but drops those fields. Extend its explicit allowlist rather than forwarding `to_dict()`, which can contain recipient data and omits parse-failure metadata.

Add bounded `AmazonTransactions.get_transactions(order_id=...)` retrieval using the same authenticated session. Transaction rows expose completed date, signed amount (negative charge, positive refund), payment method/last four and optional order reference. Retrieve all pages for each candidate order within existing process time/output bounds; an interrupted, truncated or malformed fetch cannot establish completeness. Preserve repeated equal-valued occurrences. The JSON parser currently takes only the first `orderData` entry: retain/detect multiplicity before relying on the parsed single reference, and reject multi-order ambiguity rather than silently assigning the whole charge to the first order.

Shipment item groups and optional tracking-derived shipment IDs are available, but there is no direct charge-to-shipment/item map, stable transaction ID or per-item tax/discount allocation in the public models. `full_details`, `item_count` and `parse_failures` are useful checks, not completeness guarantees. Missing quantities must remain unknown rather than using our existing display fallback of 1 as accounting evidence. Currency symbols are stripped and amounts can be floats; validate site/currency policy and exact decimal cents locally.

An upstream coupon fixture yields subtotal $36.71, coupon −$3.89, tax $2.71, gift-card funding −$35.53 and details grand total $0.00. The library can also preserve a history grand total when cloning into details. Record/reconcile field provenance and distinguish full order value from remaining payable/card amount. Gift cards and reward payments are funding, not automatically merchandise discounts. This research proves available parser capabilities, not current live-account coverage; fixtures and a later explicitly authorized read-only account check must qualify actual page support.

## Shared classification boundary

Use one `ItemClassificationService` to own decision resolution: approved mapping precedence/conflicts, policy-scoped inferred cache lookup, batching and validated remote decisions. Extract the current HTTP implementation into `RemoteItemClassifier` rather than maintaining Amazon/Walmart subclasses or duplicating adapters. Names are proposed; responsibilities and neutral dependencies are the contract.

The input is a small neutral item record (local correlation ID, optional retailer product ID, title) plus explicit retailer, plan and category-policy context. The output is a decision per local ID with nullable category, source, acceptance/provenance and failure status. Monetary values, order allocation, account selection and YNAB writes stay outside classification. Extract only a tiny value type if it simplifies the existing typed contract; do not create a general retail-order hierarchy.

Move shared category catalog validation out of `WalmartAllocation`: it validates eligible IDs and descriptions without requiring a default. Walmart additionally validates its required default against the selected list. Product text and source `category` strings are untrusted evidence, never authoritative YNAB IDs.

Reuse the existing provider implementation, endpoint/model restrictions, response validation, credentials protection, limits and metrics without broadening providers or silently changing Walmart policy. Remove Walmart-specific grocery assumptions from the Amazon instructions. Keep the current Walmart prompt/policy fingerprint stable during the refactor; introduce a distinct Amazon policy version and invalidate caches when semantics change. No cross-retailer batching, cache reuse or learning in the first version, even if titles or ASIN-like identifiers happen to match.

Keys for inferred decisions include retailer, plan, stable product ID when available, title, shortlist IDs/current labels/descriptions, provider/route/model, prompt/policy version, acceptance gates and connection identity. Approved mappings are scoped to retailer/plan/product and revalidated against the current shortlist. Without a trustworthy product ID, classify by local row correlation but do not persist product learning. Conflicting approved mappings remain unresolved and do not get overruled by inference.

Generalize provider-key storage and category-selection mechanics, not just class names. Keep separate retailer configuration references and consent: existing Walmart consent does not authorize uploading Amazon purchases. Shared credentials may be explicitly selected after disclosure; separate connections are supported. Disconnect must not delete a credential still referenced by the other retailer. Existing Walmart flags and files continue working; no forced credential rotation or journal reset.

Pull up `YNABService` plan currency/category/account/fresh-transaction/PUT methods into neutral names and reuse its current guarded transport. Reuse durable-intent, eligibility and read-back mechanics where both orchestrators need them, keeping retailer-specific plan construction and fingerprints outside. Extract protected atomic file/locking mechanics if needed by both stores; do not make Amazon depend on a class named `WalmartJournal` or generalize the Walmart ledger model. Avoid a pluggable framework with no second concrete use.

## Amazon financial evidence and allocation

Initial financial scope: complete USD purchase orders with one evidenced external payment, optionally supplemented by known gift-card funding, and one uniquely eligible YNAB outflow matching the external charge exactly in integer cents. Fully gift-card-funded orders need no YNAB transaction or write. Verify source and plan currency, all item costs/quantities, all adjustments, payment coverage and global transaction/order uniqueness. A high legacy match score or coincidentally equal order total is insufficient. Duplicate email/CSV/Python representations must resolve consistently by order ID or block allocation; do not add duplicate items or let source ordering decide conflicting costs.

### Sufficient confidence means every financial gate passes

There is no weighted confidence percentage that can compensate for missing money. All purchase gates below must pass before assigning item categories or splits; refunds use the event-specific gates rather than requiring a single original purchase charge. Allocation failure uses the linked uncategorized fallback below when its order association and write eligibility are independently trustworthy. Otherwise leave the transaction unchanged. Preview lists failed gates rather than reporting only a generic low score.

### Allocation failure retains metadata and explicitly clears the category

In opt-in `item_categories` mode, a trustworthy eligible order match with insufficient allocation evidence must still receive the robot marker, known order date/total/currency, compact available item summary and complete mobile order link. Explicitly send `category_id: null` with the memo and `approved: false`, without subtransactions; omitting the category field is not sufficient. For refunds retain known credit metadata and the original order link, without inventing refunded item membership. Unknown metadata remains unknown, not zero or inferred. This linked uncategorized fallback also applies when necessary classification fails operationally. It does not require reconciled item amounts merely to preserve the association and request manual category review.

This is a guarded category write, not an exception to ownership safety. Require an unapproved, unsplit, otherwise eligible fresh parent with either an already-null category or trustworthy app-owned category provenance; never clear a non-owned human category, overwrite existing splits or unapprove reviewed work. Ambiguous order association, changed parent, insufficient memo space or unresolved prior write outcome blocks the fallback. Preserve bank amount and identity; journal intent and read back both memo and null category before declaring fallback applied. Record allocation as still incomplete so later evidence can enable categorization without duplicating metadata or clearing a subsequent human correction. Dry runs preview the exact null field without writing. The existing default `memo_only` mode remains memo-only and does not gain category-clearing writes.

Use three distinct outcomes throughout: `memo_only` mode writes metadata only; `item_categories` mode either applies evidenced item allocation or the guarded linked uncategorized fallback. If association or write safety fails, leave the parent unchanged. The fallback is a category write and must never be described as “no financial writes.”

### Payment identity and fallback association are explicit

Proposed `amazon.payment_accounts` maps normalized source payment identities (method plus last four, namespaced by source where needed) to existing YNAB account IDs within the selected plan. Setup confirms the mapping; account names, payees, amount proximity and last four alone cannot establish identity. Validate open on-budget account targets and reject conflicting identities; several confirmed source identities may map to one account. Preserve the mapping identity in evidence/journal fingerprints; changing it cannot redirect an applied transaction. Do not inherit Walmart mappings or equate card-network labels with YNAB account names.

The linked uncategorized fallback requires a validated real order ID and an unambiguous association to that specific bank transaction: either a uniquely matched completed source payment event (signed exact cents, confirmed account identity and date within 14 days), or trusted existing journal association with unchanged bank identity/amount and no contradictory source evidence. Missing item costs or incomplete adjustment details may prevent allocation without invalidating this event match. A legacy score, robot memo, processed-ID entry, order total alone or generic email title is not sufficient. Competing known event assignments block fallback even if item details are otherwise complete. If event identity/completeness is itself uncertain, keep display records available for preview but do not clear categories or write guessed metadata.

| Gate | Required evidence | Example failure reason |
|---|---|---|
| Source coverage | Real order ID, supported noncancelled purchase, full item detail and completed order-specific charge-history pagination; no relevant parse failure, conflicting duplicate source or count mismatch. `full_details` alone is insufficient. | `incomplete_source` |
| Currency and amounts | Verified USD plan and source currency policy, no contradictory currency evidence, unambiguous extended item costs/quantities, finite amounts convertible to exact cents. Preserve unknown versus genuine zero. | `unknown_item_basis` / `unsupported_currency` |
| Payment coverage | Full reconciled order value equals known gift-card funding plus exactly one supported external charge. Without gift cards the external charge covers the full value. No unexplained funding, reward payment, additional external charge or pending/unsupported event. Fully gift-funded orders have no bank allocation. | `unsupported_payment_coverage` |
| Unique bank association | Same real order reference, exact signed cents, known compatible payment-method/account identity, charge-completed date within the existing 14-day matching ceiling of the YNAB date, and a globally unique one-to-one assignment. Ties, missing identity or a one-cent difference fail. | `ambiguous_payment_match` |
| Explained costs | Item extended costs plus explicitly identified, nonoverlapping discounts/tax/shipping/fees explain full order value exactly. Null optional fields need validated absence/zero semantics for that source layout; no inference of tax from a residual or addition of overlapping aggregate discounts. | `unreconciled_costs` |
| Exact allocation | The approved adjustment policy yields nonnegative per-item cents whose sum is exactly the parent outflow magnitude; signed YNAB milliunits sum exactly to the existing parent. Only distributing known amounts may round. | `allocation_mismatch` |
| Write ownership | Fresh parent is eligible and unchanged against baseline; memo fits; journaled ownership/recovery checks pass and no human category/split is overwritten. | `parent_changed` / `ineligible_parent` |

Financial reconciliation uses zero tolerance: no one-cent matching allowance and no plug line. Date proximity is a candidate bound, not a substitute for order/payment identity. Fetch completeness is an observed source-contract result, not a claim that the unofficial website parser can guarantee Amazon's future behavior; unknown layouts fail closed.

Category confidence is separate. Accept an unambiguous approved mapping within the Amazon shortlist, or a valid provider result meeting all configured gates (initial defaults: chosen probability at least 0.80, independent confidence at least 0.80 and margin over the runner-up at least 0.20). These scores are acceptance thresholds, not a promise of 80% correctness; Amazon quality must be qualified separately. A valid low-score/abstention or mapping conflict produces a null-category item line if financial gates pass. Malformed responses, unavailable necessary inference or transport failures block item allocation but still permit the independently guarded linked uncategorized fallback. The model never supplies item costs, payment completeness or adjustment attribution.

Expose evidence completeness separately from legacy defaulted model getters. Extend source normalization only where fixtures establish meaning; do not manufacture payment completeness or infer tax from an unexplained difference. Missing item/adjustment evidence blocks item allocation; use the guarded fallback only if its independent association/write gates pass, otherwise leave unchanged. Synthetic `SUB-` IDs cannot qualify for linked fallback. Preserve source selection, S&S/login-notice behavior and default memo-only compatibility while enhancing refund evidence below.

Every item with a nonzero bank allocation becomes an item line with its classified category or null for review. Keep one line per source item identity, including quantity in the memo when greater than one; do not merge different products just because categories match. Repeated ASINs still have distinct local row IDs. Zero-cost or zero-bank-allocation items may remain in the parent summary but emit no zero line. For one nonzero row, use a category-only write and preserve item text in the parent; for multiple nonzero rows, retain itemized rows even if all categories agree, so correction/learning stays attributable.

**Decided adjustment policy:** allocate known tax, shipping and fees proportionally across item splits. Apply discounts directly to the identified item when reliable source evidence establishes the association; if item attribution is absent, distribute the explicitly known discount proportionally. Lack of item attribution is acceptable; an unknown discount amount or unexplained residual is not. Do not ask the classifier to guess which item earned a discount.

Apply extended item costs and item-attributed discounts first. Allocate each remaining discount over the applicable items' current net merchandise costs (all items unless evidence limits eligibility), using stable source adjustment order; then allocate each positive tax/shipping/fee independently over the final discounted merchandise weights, not over amounts inflated by earlier tax/fees. Use largest-remainder integer-cent rounding with stable local item-ID tie breaks at each allocation. Each known adjustment is counted once; aggregate totals such as total-before-tax are reconciliation checks, not extra charges. Reject negative item amounts, unsupported overlapping discount semantics and nonzero adjustments with zero total weight. Never create a balancing/default remainder. This is the user's budgeting convention, not a claim about exact item tax liability.

Worked examples (synthetic): a $20 cable and $40 pet-food item plus $5 explicit order tax yield $21.67 and $43.33 after largest-remainder rounding, summing to $65.00. With a $6 explicit order discount and $5 tax, net merchandise is $18/$36; tax allocates $1.67/$3.33, yielding $19.67/$39.33, totaling $59.00. If only the $65 grand total and $60 merchandise are known, the unexplained $5 is not assumed to be tax and allocation skips. Provider errors block item allocation, not the eligible linked uncategorized fallback; valid abstention still permits an uncategorized item row.

If that $6 discount is explicitly associated with the cable instead, net merchandise is $14/$40; $5 tax allocates $1.30/$3.70, yielding $15.30/$43.70, still totaling $59.00. This asymmetric example distinguishes item-specific attribution from the proportional fallback. A $3 shipping fee on $20/$40 net merchandise allocates $1/$2.

### Gift cards fund the order; they do not select items

First reconcile the full order and compute each item's adjusted full-order cost using the discount/tax/shipping policy above. Then verify that the known gift-card amount plus the external charge equals that full order value exactly. Never infer the gift-card amount solely from the gap between order and bank totals. Classify every order item, not a guessed card-funded subset. Allocate the remaining bank charge proportionally across the adjusted full-order item costs with largest-remainder integer-cent rounding and stable item-ID ties. Do not subtract the gift card as a merchandise discount, create a gift-card category/offset line, create a separate transaction or change the bank parent amount. Apply the funding reduction once, after all order adjustments.

For example, $20/$40 merchandise plus $5 tax gives adjusted item costs $21.67/$43.33. With $15 gift-card funding, the $50 bank outflow allocates $16.67/$33.33 (YNAB −16670/−33330 milliunits), not the full $65 and not only one item's cost. With the cable-specific $6 discount, adjusted costs are $15.30/$43.70, totaling $59; $10 gift-card funding leaves $49 to allocate as $12.71/$36.29. These weights include item-specific discounts and allocated tax, rather than raw merchandise alone. Classify positive-cost items even if a very small external amount rounds an item's bank allocation to zero; omit zero-value rows but retain their classification/provenance. A single nonzero row uses the category-only optimization while the parent summarizes the full order.

The parent memo retains full order `Total` and additionally labels `Gift card $15.00 | Charged $50.00` for the first example, subject to the same required-metadata space checks; generated item titles yield first. Preview distinguishes full item costs, gift funding and final bank allocations. If gift cards cover the entire order and no external charge exists, do not require a YNAB match, create a synthetic transaction, submit financial writes or report an unmatched bank transaction. No remote classification is needed solely for an order with no YNAB target. A zero details grand total alone does not prove full gift-card funding.

Future multiple-external-charge purchase support requires its own explicit payment evidence and allocation policy, not reuse of Walmart's descending-capacity convention by accident. Known gift-card funding plus one external charge is supported now and is not part of that deferral. Refunds use the separate event-level policy below; do not assume a refund returns through the original funding proportions or import Walmart's default-refund fallback.

## Refund matching, categories and conditional item splits

### Match the credit event, not the original order total

Fetch signed refund-credit occurrences from transaction history independently of purchase eligibility. Discover recent credits with the configured transaction lookback, then fetch original order details by real order ID as needed even when the purchase predates the normal order-history window. Bound detail requests and paging using the existing process limits. If details are unavailable, a unique event match may still produce a refund-only memo/link, but not guessed item allocation.

Match positive YNAB inflows to positive refund events with exact signed cents, compatible refund payment/account identity and a completed date within the 14-day bank-date ceiling. Use the refund's payment destination, not an assumption that it returned to the original purchase account. Resolve candidates globally, consume each event once and skip indistinguishable assignments. Keep distinct equal-valued credits and multiple credits for one order. The order's `refund_total` is cumulative supporting evidence, not an event identifier, refund amount or proof of item attribution. No original-order-date grace heuristic substitutes for the refund date.

Use separate purchase/refund event namespaces in normalized models and journal keys. Prefer a stable upstream event/source ID when available; otherwise persist an occurrence-aware identity with source provenance and multiplicity, never only order ID or array position. If equal occurrences cannot be distinguished consistently across snapshots/restarts, stop for review. Email and transaction records corroborating one credit must not count as two credits; conversely, do not collapse distinct same-order refunds. Legacy `RETURN-` records are not provenance for automatic historical category rewrites.

### Obtain item evidence without assuming the library supplies it

The pinned library's `Transaction` has no item rows, `Order.refund_total` is aggregate, `Item.return_eligible_date` does not mean an item was refunded, and invoice/credit-note objects contain document metadata rather than parsed refund line amounts. Extend the existing email parser to retain all explicit refund item rows, ASIN/order-line references where present, quantities, event/reference identifiers, dates, currency, item refund bases, discounts and refunded tax/shipping/fee components. Preserve nullable values and whether the amount was a subtotal or final credit; a generic title, first extracted title or subtotal-only fallback is not a verified single-item net refund.

When email is the selected automatic source, use this enhanced parser within the existing IMAP workflow. Python mode may opt into `amazon.refund_email_evidence.enabled: true` with explicit IMAP configuration; default false, no silent mailbox access or purchase-source change. Proposed `amazon.transaction_evidence.enabled` defaults true in Python purchase mode and false in email/CSV-only mode. Enabling it outside Python mode requires explicit opt-in and existing Python session/runtime settings; paths alone do not authorize launching it. It supplies purchase as well as refund payment events without replacing purchase ingestion. Email/CSV-only runs lacking qualified event evidence remain nonallocating; raw email totals alone do not qualify for category-clearing fallback. Normalize optional source evidence in Groovy; do not require another classifier or make email mandatory for Python operation.

Only explicit source association may establish refunded item membership and quantity. A uniquely linked single-item original order with a confirmed monetary refund can establish the sole product, but not the refunded quantity or adjustment breakdown without further evidence. Trusted original purchase provenance may supply known item bases where the refund explicitly confirms a full reversal of those identified quantities. For multi-item partial refunds, a matching subset sum, amount similarity, model inference or the original order's full item list is not sufficient. Missing item attribution yields `refund_items_unknown`; known items without reconciled per-item amounts yield `unreconciled_refund`. Both use the guarded linked uncategorized fallback when independently eligible, otherwise leave the parent unchanged.

### Apply refund-specific financial and category confidence

Refund allocation requires complete evidence for the individual credit: unique event/account/date match, verified USD, identified refunded items/quantities or explicit final per-item credits, known amounts and adjustments, no conflicting duplicate evidence, exactly reconciled nonnegative item nets and an unchanged eligible positive YNAB parent. It does not require the original purchase to be in lookback, categorized by this app or single-payment. Cancellations and past order refunds do not invalidate an independently supported credit. Gift-card/reward/mixed-tender refunds, pending credits, amount-only goodwill credits, uncertain event-to-item association and unsupported fee-only/negative-net cases block item allocation. A completed external credit with trustworthy association may still receive guarded linked uncategorized fallback; pending or ambiguous events do not. Other credits on the same order may be unresolved without blocking an independently proved event.

For each identified item, first reuse an unambiguous human-approved original purchase-item category with trustworthy saved provenance, provided it remains eligible and in Amazon's shortlist. Do not reuse an aggregate purchase parent category or another item's category as a default. Conflicting approved original-item/product evidence remains unresolved; a known original category outside the shortlist is preserved on the original purchase but not silently replaced by a model-selected refund category. Without usable original-item evidence, use shared approved mappings and provider acceptance on the refunded item's title. Valid abstention permits null item categories when finances reconcile; inference failure blocks item allocation but permits independently eligible linked uncategorized fallback. Do not edit the original purchase or approve the credit automatically.

Use actual refund net amounts, not original purchase allocations multiplied by a guessed percentage. Apply explicit refund item discount deductions to that item; unknown attribution of a known event-level deduction uses proportional weights over identified refund merchandise. Add only tax/shipping/fees actually refunded, proportionally over the final net refundable merchandise; never assume original shipping or all original tax was refunded. If the source supplies final net item credits, use them as final values and do not add their components again. Explain withheld fees explicitly before proportional deduction; unsupported mixed-sign results skip. Apply the same deterministic cent rounding, no residual plug and no unrelated-item remainder rules as purchases.

Example: an evidenced credit refunds cable merchandise $20 and pet-food merchandise $40 plus $5 explicitly refunded tax. Write positive split amounts $21.67/$43.33 (YNAB +21670/+43330 milliunits), totaling +$65.00, with each item's category and title. If the cable's $6 promotion is deducted from this credit, cable/pet merchandise is $14/$40 and refunded tax of $5 gives +$15.30/+$43.70, totaling +$59.00. A uniquely matched eligible +$65 credit without refunded-item evidence receives metadata/link and explicit null category, not item allocation, regardless of classification confidence.

Refunds omit zero-net rows while retaining their item evidence. One nonzero refunded-item allocation uses a positive category-only write; multiple nonzero allocations use positive item splits, retaining separate rows even for the same category. An unresolved category remains null, never Income/Ready to Assign or a Walmart default. Keep parent amount/account/date/payee/import/cleared/flags unchanged, write `approved: false`, fresh-check baseline, journal intent and read back uncertain outcomes exactly as for purchases. Learning from approved refund rows requires the same item provenance and conflict rules and must not duplicate its original purchase observation as extra evidence. Never learn a zero-allocation item's category from the sole nonzero parent category.

### Refund memos and recovery

Use `🤖 <credit-completed-date> | Refund $<credit-total> USD | <refunded-item summary> | <mobile order URL>`, not `Total` labeled as the original order value. Split rows use `🤖 Refund: <item>` with quantity only when known. A memo-only credit with unknown products omits invented item names. Preserve user text and the complete URL under the same 500-character rules. Resolve validated legacy `RETURN-<real ID>` to the real ID for the URL while retaining its refund-event identity internally; never put the synthetic prefix in the link.

Journal event-to-item and row provenance, completion, observations and applied intent separately per credit. A later refund for the same order is a new event, not drift of a previously completed refund; a changed amount/item assignment on an already applied event is drift and stops further writes. Repeated email notices, credit history rows, accepted-but-response-lost writes and restarted runs must not create duplicate allocation, repeat category-only writes or reopen human-reviewed credits.

## Parent and split memos

For fully evidenced purchases, generated parent content starts with `🤖`, ISO order date and full positive order total/currency, then up to three shortened item titles and the complete direct URL last. Fallbacks retain all known metadata but omit unavailable date/total/item fields rather than inventing values; the robot, user text and validated real order link remain required. Credit memos label known credit date/amount as Refund, never substitute those for the original purchase date/total. Keep S&S/return context when applicable. Example with no existing memo:

```text
🤖 2026-11-20 | Total $65.00 USD | 2 items: USB-C cable, Dog food | https://www.amazon.com/your-orders/order-details?orderID=113-8849250-2919462
```

When user text exists, retain it intact after `🤖 ` and before the generated date block, separated by ` | `; never move or truncate that text merely to improve phone previews. Reserve room for marker, user text, date/total/currency and URL first, then fit the summary into remaining space. Shorten generated titles with an ellipsis and item count; omit titles only if no title fits. If required fields cannot fit in 500 characters, skip that parent's entire update, including category writes. Do not run the legacy ASCII sanitizer over the robot/link or truncate the URL. Preview must show exactly what would be written.

Construct the URL locally only for validated real order IDs matching the supported Amazon numeric format; never trust an arbitrary source URL. The exact format is `https://www.amazon.com/your-orders/order-details?orderID=<order-id>`, including case-sensitive `orderID`. The order ID is already in the URL; avoid repeating it as `#...` unless subsequently requested. Synthetic S&S identifiers cannot be put in that URL: retain a clearly labeled no-link summary until a real ID exists. This format is requested for mobile compatibility; actual app handoff was not tested in this proposal.

Split examples: `🤖 USB-C cable` and `🤖 2 × Dog food`, with null category for unresolved lines. Bound generated line titles to 500 characters without cutting the marker; retain full identity/provenance in the protected journal. The robot identifies generated content, not a confident classification. Preserve product names without Walmart's metadata-only parent rule leaking into Amazon.

## Safe rollout and recovery

Land a behavior-preserving refactor with existing Walmart tests first. Preserve existing Walmart config paths, CLI, provider prompt/version, cache keys and journal format where behavior is unchanged; any required state migration must be explicit, atomic and prove recovery of pending writes. Amazon starts with a separate versioned store scoped by retailer/plan/order/transaction; no automatic conversion of Walmart records or legacy processed IDs.

For the new Amazon workflow, replace memo-length/content completion heuristics with journaled link/category/split states. A journaled memo-only write can later categorize if its saved state still matches the fresh parent. Legacy processed IDs remain excluded by default; they convey no item provenance.
