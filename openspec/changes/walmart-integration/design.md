# Walmart integration design

Use the reviewed Go client to link each YNAB purchase to a distinct Walmart final charge, then optionally concentrate non-default items in the fewest charge transactions with sufficient capacity. Categorize the remainder to the Default Walmart Category without itemizing groceries. Exception-first allocation mirrors the user's bookkeeping workflow; it does not identify which items Walmart actually charged together.

This is a proposal only. No Walmart implementation, login or YNAB write is authorized by this document. See `proposal.md` for motivation and the capability specs for normative requirements.

## Context

- The nonworking browser-backed guest/login fetchers, Playwright dependency and obsolete Walmart settings have been removed without backwards compatibility. Walmart fetching is unavailable: only `walmart.enabled` remains recognized, defaults to `false`, and reports an explicit unavailable error when `true`. Existing models, matcher and processor remain. `TransactionMatcher` compares final charge amounts but does not reserve unique charge occurrences and also permits an order-total fallback; the replacement must enforce the new ledger contracts throughout Walmart matching.
- `TransactionProcessor` already adds Walmart links. Transaction DTOs and `YNABService` need category, split, approval and read-back support; the existing processed-ID/memo heuristic cannot represent link-only versus category/split completion and subsequent human review.
- Reviewed client: [`github.com/eshaffer321/walmart-client-go/v2`, v2.2.1](https://github.com/eshaffer321/walmart-client-go/tree/d908f3d31ae1be088ad4a02ebe7f0b3dd2f70244). `ledger.go` exposes payment identity and final charge amounts/dates, but no charge-to-item mapping. `models.go` exposes item quantities and prices. Neither grouping by shipment nor repeating all items per transaction is justified by this evidence.
- [YNAB OpenAPI](https://api.ynab.com/papi/open_api_spec.yaml), freshly inspected version 1.91.0, supports converting an unsplit transaction through the current canonical `PUT /plans/{plan_id}/transactions/{transaction_id}` route with `subtransactions` and parent `category_id: null`. The implementation URL choice will be verified during apply. It rejects updates to existing split subtransactions. Amounts use integer milliunits; omitted `approved` defaults to false. The implementation must preserve parent state explicitly.

## Goals / Non-Goals

**Goals:** Match individual charges without reuse; preserve order access; minimize transactions needing exception review; allocate exact totals using only existing categories; use YNAB approval/corrections as feedback; retain user edits and safe retry behavior; keep session and purchase data local/minimal.

**Non-goals:** Reverse-engineer an actual item-to-charge mapping; create, rename or suggest new budget categories; retain proportional allocation; add a hosted classifier; split refunds or foreign-currency transactions; edit existing splits; replace imported bank transactions; build a new review GUI; guarantee atomic updates across multiple transactions; change Amazon behavior.

## Decisions

### 1. Put the Go client behind a small repository-owned helper

Add a dedicated Go module/helper using the reviewed revision with checked-in `go.mod`/`go.sum`, a documented toolchain and `go mod verify`. Expose a versioned JSON output contract to a new Groovy fetcher used by `WalmartService` as its sole fetching source when enabled. Standard Java distribution must still run without Go/helper installation when Walmart is disabled. Do not restore browser guest/login modes, their configuration or Playwright, and do not add compatibility aliases or fallback sources.

#### Gradle owns the optional Go build lifecycle

Use an explicit build property, `-Pwalmart`, independent of runtime YAML's `walmart.enabled`. Without it, existing Gradle tasks neither resolve/download Go tooling/modules nor compile/package the helper. With it, Gradle provisions an exact pinned Go SDK for the build host into its cache, verifies the checked-in platform archive digest before extraction/execution, and invokes that SDK rather than whichever `go` happens to be on PATH. Keep module versions/checksums read-only and disable Go's implicit toolchain switching/downloads. Select a maintained SDK compatible with the reviewed module during apply, not a floating latest version. A populated cache supports offline builds; missing SDK/modules under `--offline` fail clearly without network access.

Wire the existing lifecycle rather than requiring a parallel Makefile or manual Go commands:

- `classes -Pwalmart` compiles the helper; `testClasses -Pwalmart` also compiles its test code without running tests, matching the repository's existing build script contract.
- `test`/`unitTest -Pwalmart` include Go unit tests; `integrationTest -Pwalmart` includes offline Go/helper contract tests; `testAll`/`check`/`build -Pwalmart` include both through their existing dependencies, without duplicate Go runs. Go test/build failures fail Gradle and test reports are published alongside JVM results.
- `installDist`, `distZip` and `distTar -Pwalmart` depend on the compiled helper and package it with the onboarding script and launch-time helper discovery. Model weights, Hugging Face tokens, sessions and the Go compiler are not distribution contents. Runtime model provisioning remains an explicit onboarding step.
- `clean` removes generated Go outputs under `build/`, not the shared verified SDK/module caches. Declare source/module/toolchain/target inputs and outputs so up-to-date checks and switching enabled/disabled builds cannot reuse a stale helper or accidentally package one into the base distribution.

Start with a native helper for each explicitly supported build-host OS/architecture; label Walmart distribution artifacts with that target so they cannot be mistaken for portable JVM-only archives. CI runs both base and Walmart-enabled Gradle lifecycles and package smoke tests, including JVM-to-helper fixtures without credentials, on supported release targets. Do not claim untested cross-compilation or package an executable for the wrong target. Consumers of a Walmart-enabled distribution need no Go installation; users who installed the base distribution need the matching Walmart-enabled package before enabling fetching, with a clear missing-helper message. No runtime compilation or SDK download occurs. Build automation must not read account credentials or enable Walmart; its opt-in controls packaging only. Optional model runtimes remain separately provisioned, not downloaded by Gradle tests/distribution tasks.

Input consists of a protected local session-file path and non-secret query bounds. Session capture import must parse data without executing pasted cURL/shell. Owner-only permissions or equivalent ACLs protect bearer material. Fetching never automates login, requests a password or reads email. Ship explicit setup/expiration/disposal instructions; credentials and capture contents never enter command arguments or logs.

Apply positive HTTP/process timeouts, pagination bounds, output-size limits and version/schema checks. Enforce verified TLS, exact required Walmart hosts and no off-site redirects, including session/configurable URL inputs; constrain or replace unsafe client defaults rather than trusting upstream validation. Use a source-specific child-environment allowlist and minimal session/output fields. Do not relax the Amazon runner's protections to accommodate Walmart.

Process/environment bounds are not an OS sandbox. Document dedicated unprivileged execution and narrow filesystem/network access for deployments needing isolation. Do not add the client's optional browser installation or debug/raw-response persistence to the normal path.

**Alternative rejected:** Embedding the entire upstream CLI/browser workflow exposes more state and behavior than the application needs. Copying its implementation into Groovy loses the reviewed dependency boundary.

### 2. Normalize a complete ledger before matching

The helper emits order ID/link, order placement date, full order total/currency, fulfillment state, item IDs/descriptions/decimal quantities, extended costs and known discounts/tax/fees/tips, plus every final purchase-charge occurrence with currency, date and payment identity (type/card type/last four when available). Emit completeness and failure state explicitly; omit addresses, cookies and unused response fields. Missing or uncertain order metadata prohibits metadata enrichment rather than substituting the bank transaction's date or amount.

Normalize raw decimals directly where possible. The client uses `float64` for some ledger values: convert only finite values demonstrably representing exact cent amounts within bounded machine-representation error; reject materially fractional-cent values, never use a broad matching tolerance. Use decimal/integer cents after this boundary. Reject unsupported currency or unknown currency rather than assume USD from a numeric value alone.

Deduplicate repeated presentation groups by stable item identity without collapsing genuinely separate lines. Use extended costs as supplied, not extended cost times quantity. Preserve separately identified discounts and distinguish pre-discount extended item prices from already-net prices. Reconstruct a pre-discount price only when an explicit corresponding discount proves it; never add a discount back twice. Unknown discount semantics prohibit category allocation. Keep taxes, fees, tips and discounts as evidence in the local plan, but book their signed net effect entirely to the Default Walmart Category, not separate YNAB component lines or exception categories. Never manufacture an adjustment to hide an unexplained discrepancy.

Canonical charge keys use order ID, payment identity, date, amount and a duplicate ordinal for identical occurrences; do not invent upstream transaction IDs. Treat indistinguishable duplicate occurrences as a multiset and retain multiplicity. Unknown/misaligned dates or incomplete charge lists cannot produce a split-ready order. Holds/refunds are not purchase columns. Pending fulfillment, unresolved cancellations, refunds or uncertain pricing make the order link-only at most; a split-ready snapshot must account for all fulfilled billable components and complete final purchase charges.

### 3. Match globally before reserving charge occurrences

Construct candidates using exact outflow magnitude, configured charge-date window and compatible account/payment evidence. Account mapping is optional only when the remaining evidence gives a unique assignment. Resolve the candidate graph across orders and transactions, consuming each occurrence once; skip ambiguous connected assignments rather than greedily taking the first amount match. Interchangeable identical occurrences within one order/payment are equivalent only when the set of assigned YNAB transactions is itself unambiguous.

Do not use a whole-order amount fallback for Walmart matching. Retain the stable charge key in `TransactionMatch`, not merely an order pointer. A trustworthy match may support linking even when allocation is unsafe. Generated parent memos contain only order placement date, full order total with currency, order ID and the direct HTTPS order URL; never an item list or product summary. Preserve existing user text and append the metadata once, within 500 characters. If it cannot fit, skip/report rather than truncate user text, omit required metadata or shorten the URL through a third party.

**Illustrative parent memo for either charge of the $100 example:**

```text
2026-11-20 | Total $100.00 | #1234567890123 | https://www.walmart.com/orders/details?orderId=1234567890123
```

Optimize the generated block for narrow memo previews: put the ISO order date and `Total` amount first, followed by the order ID prefixed with `#`, with the direct URL last. Omit `Order date:`, `Order ID:` and the redundant `Walmart | ` prefix because their meaning is supplied by the format and payee. Keep the unambiguous ISO date and format supported USD totals with `$` and two decimal places. `Total` always means the full order total, not the individual charge. Actual visible characters vary by device and YNAB client; do not assume a fixed preview length. Existing user text remains preserved ahead of the appended metadata.

The order date is not the bank posting date, and the explicitly labeled order total is not the individual $70/$30 charge. The transaction amount remains unchanged. Only exception item descriptions appear on their corresponding split lines; default-category item lists and non-item adjustment lists do not enter parent memos.

**Why the parent memo:** The freshly inspected YNAB public OpenAPI 1.91.0 schema has no purpose-built URL, external-link, attachment or custom-metadata field in `SaveTransactionWithOptionalFields`, `SaveSubTransaction`, `TransactionSummaryBase` or `SubTransactionBase`, and its endpoint list has no attachment endpoint. `memo` is writable with a 500-character maximum. `import_id` is import/deduplication identity, not link storage, and cannot be changed on existing transactions. Keep the order URL in the parent memo rather than repurposing identity fields. Whether a YNAB client renders that URL as clickable has not been tested and is not guaranteed.

**Clickability is a client feature:** YNAB's [Big Box Links](https://support.ynab.com/en_us/big-box-stores-Bkp2C7Vykl) provide a native, payee-detected Walmart order-history shortcut on web/iOS/Android, not a public API field for setting our matched order URL. Toolkit for YNAB has optional [hyperlink](https://github.com/toolkit-for-ynab/toolkit-for-ynab/blob/631c914714e747e0b4478e3ac521057761622bcd/src/extension/features/accounts/link-in-memo/utils.js) and [Markdown memo](https://github.com/toolkit-for-ynab/toolkit-for-ynab/blob/631c914714e747e0b4478e3ac521057761622bcd/src/extension/features/accounts/memo-as-markdown/settings.js) features. Its basic hyperlink helper treats the memo as a single HTTPS URL, so it does not safely linkify the mixed metadata format above. Markdown rendering is optional extension behavior, not an API guarantee. Keep plain text/direct URLs as the portable format; do not install an unaudited extension or change memo formatting solely to satisfy it. We have not verified current native memo link rendering or audited Toolkit as a whole.

**No URL shortener:** A shortener does not make plain memo text clickable. Third-party shortening exposes the destination/order ID to another operator and adds redirect availability, retention and destination-integrity dependencies. Removing item lists leaves ample space for a direct URL in ordinary memos. Keep the validated Walmart URL, without marketing/tracking parameters or session tokens; never send order URLs to a shortening service. Self-hosted redirects add operational complexity without solving client rendering.

### 4. Map exceptions only to existing budget categories

Require `default_category_id` and an explicit `categorization.categories` shortlist of existing eligible category IDs in the configured YNAB plan. The default must occur in that list; Groceries is the user's example, not a category to create automatically. The intended list is roughly 10–20 Walmart-relevant categories rather than the whole budget, but there is no arbitrary fixed category-count limit. Read and validate the catalog before writing. Reject duplicate IDs, an empty list, an absent default and hidden/deleted/special credit-card-payment targets. Category IDs are plan-scoped: renaming preserves a valid mapping, deletion or removal from the shortlist invalidates it. Never create, rename or suggest new budget categories, including when learning from human edits.

Use an unambiguous approved stable-product mapping first, provided its target remains allowed; otherwise ask the configured local decision model to score the entire supplied shortlist plus an internal abstain choice. Supply current category names and optional user descriptions of their boundaries, but map results through stable choice IDs, not generated category names or row positions. No category discovery or generative category suggestions occur. Validate finite scores, candidate membership and configured acceptance/margin thresholds in application code. Probabilities are model scores, not guaranteed correctness; calibrate thresholds on held-out representative Walmart examples, including non-grocery exceptions and ambiguous products. A confident default decision collapses into the default remainder. Missing information, low confidence, conflicting approved mappings, invalid output and model failures produce uncategorized exception items for YNAB review; they never silently mean Groceries. An error affecting the model batch leaves its unresolved items uncategorized or the order link-only if the safe plan cannot be formed. Do not partially accept malformed batch output.

Illustrative future YAML shape (placeholder IDs refer to existing categories; this is not currently supported configuration):

```yaml
walmart:
  default_category_id: existing-groceries-id
  categorization:
    provider: laya # sole initial provider; Kev deferred
    model_manifest: /protected/models/walmart-model.json
    categories:
      - id: existing-groceries-id
        description: Food and beverages for people
      - id: existing-household-id
        description: Cleaning products and household consumables, not food
      - id: existing-pet-id
        description: Pet food, litter and other pet supplies
```

The model manifest identifies reviewed container-image digest and runtime/checkpoint/tokenizer/encoder revisions and hashes, device `cpu`, precision/backend, resource limits and checkpoint-specific acceptance thresholds. Category descriptions are optional local configuration, not new YNAB categories. Validate all candidates against the selected checkpoint's token/choice limits before inference; never truncate descriptions, silently drop categories or use a coarse first-stage decision that prevents considering an allowed choice. Oversized inputs abstain/report. Treat product text as untrusted data; the model has no tools, network access or authority over money, categories or API writes. Send only bounded product title/brand/variant information needed to classify and category choices, not session data, order URLs/IDs, addresses, payments or the full budget. No model arithmetic determines allocations.

An exception item mapped to the default category is part of the default remainder, not an itemized exception. Keep item identities in the plan even when many default items collapse into one remainder. Do not infer product mappings from an old Walmart transaction's overall category or from the aggregate default remainder.

#### Guided onboarding without manual category IDs

Provide a repository-owned interactive terminal script for initial setup and later reconfiguration. It operates on the selected application config and its configured YNAB plan/credentials; missing YNAB setup produces actionable guidance, not a new authentication mechanism or a guessed plan. The script performs these steps:

1. Detect the platform, Docker engine availability and Linux-container architecture, then ask for the model RAM budget before profile selection, defaulting to **1 GB** with an explicit choice up to **2 GB**; display units unambiguously (1 GB = 1,000,000,000 bytes). This budgets the container's model worker and its child processes, including runtime, model loading and inference peaks, not just weight files; the JVM, Go helper, operating system and Docker engine/VM need additional RAM. Explain Docker Desktop/VM overhead and prerequisites on Mac/Windows, without auto-installing or reconfiguring Docker. Offer only qualified Laya classic checkpoint/container profiles measured to fit that budget with documented headroom on the detected platform. Recommend the lowest-memory profile that meets the retail-quality gates, using measured CPU latency to break ties; show measured memory/latency, host overhead and disk/download size separately and the reason for the recommendation. Let the user confirm another fitting qualified profile, not silently choose it. No arbitrary Hub repository or dynamically selected latest revision. Explain missing/unqualified measurements or prerequisites rather than guessing compatibility.
2. Prompt for a Hugging Face read-access token using hidden input, with instructions to limit access to the required repositories. Use it only for explicit provisioning requests to approved Hugging Face endpoints; never forward authorization to unrelated redirect hosts. Explain that provisioning contacts Hugging Face, while later categorization stays offline and sends no purchase or YNAB category data there. Do not echo the token, put it in command arguments/config/journals/logs or persist it through a global Hub login/cache; discard it when provisioning ends. Validate required repository access without claiming this proves the token has no broader permissions. Authentication/license-access errors give retry/cancel guidance and never request write/admin access.
3. Confirm the download, provision the digest-pinned reviewed container image and complete Laya classic model/tokenizer/encoder configuration into protected staging storage, verify the pinned hashes and install atomically into a dedicated local model directory. Reuse already verified artifacts. Handle any required tokenizer normalization as a reviewed setup transformation with its own verified output hashes, never by weakening checks or allowing inference to rewrite the model mount. Interrupted, denied or corrupt downloads must not register a usable model or modify configuration. Perform the qualified offline container CPU load check before marking provisioning ready; no Walmart login or account writes occur. Do not mount the provisioning token or its credential cache into the inference container.
4. Fetch eligible existing categories read-only from the configured YNAB plan and display a numbered list with category-group names to distinguish duplicate category names. Ask for a comma-separated list of numbers, such as `1,4,7`; resolve numbers against that displayed snapshot to stable IDs. Reject empty, duplicate, malformed or out-of-range choices with a clear retry prompt, without silently selecting the entire budget. Do not display hidden/deleted/special payment categories as selectable choices or create/suggest new ones.
5. Ask which selected category is the Default Walmart Category, show the selected provider, local artifact location, category group/name/ID selections and default, and request confirmation. Revalidate the selected IDs against the same plan before saving. If a category becomes ineligible, return to selection without silently replacing it. Store `categorization.provider`, `model_manifest`, the category-ID shortlist and `default_category_id`; retain existing descriptions for unchanged IDs. Users need not copy or type IDs.
6. Save the confirmed config with an atomic protected-file replacement, preserving unrelated settings and detecting concurrent config edits rather than overwriting them. Cancellation/failure leaves the original config unchanged; do not leave a truncated config or token-bearing temporary file. Verified model files may remain for a later retry, with their location reported. Onboarding never enables Walmart fetching or exception-first writes automatically and does not reset existing operator-selected enablement/mode settings; initial defaults remain disabled/link-only. It never changes live categories or transactions. Review and approval of subsequent allocations remain entirely in YNAB.

Keep onboarding's download permission separate from the offline inference worker. Rerunning setup preselects valid saved choices but still requires confirmation for changes; no provider download or config write occurs merely by listing options. The script belongs to the later apply phase, not an action performed during proposal creation.

Save the confirmed RAM budget as `categorization.memory_limit_bytes` alongside the model selection and apply it to both provisioning's CPU load check and subsequent worker execution. On reruns, retain the valid saved budget as the initial choice. If no qualified profile fits 1 GB, explain the measured requirement and offer an explicit increase within 2 GB or cancellation/link-only operation; never raise the budget automatically. If none fits within 2 GB, do not claim support under this policy or proceed with inference. Quantized/ONNX variants need their own quality, peak-memory and platform qualification, not weight-size arithmetic. A successful installation is not evidence of fitting RAM. No latency promise is set yet; show measured expectations rather than an invented target, and stop/report if actual memory use exceeds the configured ceiling.

Initial host targets are **Linux x86_64, macOS arm64 (Apple Silicon), and Windows x86_64**, with native onboarding and CPU-only Linux containers. Windows does not require the user to run onboarding/application commands in WSL; Docker Desktop may itself use a WSL2 or Hyper-V backend and that prerequisite must be disclosed. These are qualification targets, not verified support today. Maintain a documented host/engine/image-architecture/checkpoint matrix backed by installation, offline inference, resource and isolation checks; use qualified Linux amd64/arm64 images, not silent architecture emulation. Helper binary availability does not establish model support. Check the qualified matrix and Docker prerequisites before requesting a token or downloading weights. If unavailable, preserve configuration and explain link-only operation without Docker or model provisioning. Do not silently install older dependencies, choose a GPU or use a hosted fallback.

Intel Macs remain outside the initial host target set pending separate container qualification; native macOS PyTorch wheel limitations do not determine compatibility of a Linux container. Linux/Windows ARM and other unqualified hosts likewise receive an explicit unsupported explanation rather than an incompatible image download. Publish tested engine/image/Python/dependency versions and remaining limitations per host; do not infer cross-platform support from Python or Docker availability alone.

#### Docker worker lifecycle and private IPC

The JVM directly launches `docker run` using a structured argument list, not a shell. Require an already provisioned digest-pinned image (`--pull=never`), `--network=none`, no published ports, a non-root user, read-only root filesystem and verified model mount, dropped capabilities, no-new-privileges, bounded temporary storage/PIDs/CPU/threads and enforced memory/swap bounds. Mount only the model directory read-only; never the host home, config, journals, sessions, Docker socket or credential caches. Pass only allowlisted non-secret offline/runtime environment variables, never the HF provisioning token or application secrets. Disable Docker log persistence for this worker and capture only bounded redacted diagnostics. Docker daemon access stays in the host application; it is not exposed to the model.

Start one worker per classification batch, send bounded versioned newline-delimited JSON requests with correlation IDs over stdin and validate corresponding JSON results on stdout. Reserve stdout for the protocol, bound stderr, in-flight work and total response size, and enforce startup/request/batch deadlines. Do not interpolate item text into commands, expose HTTP or invoke per-item `docker exec`. Load once for the batch, close input and remove the container on completion; on cancellation, timeout, malformed/partial output or memory failure stop/remove the identified container and leave unresolved items without writes or automatic retries that accept partial results. Verify cleanup after host interruption. Link-only/disabled operation must not probe/start Docker or download images/models.

Provisioning is an explicit separate operator step: audit and hash-lock runtime dependencies and complete model artifacts at immutable revisions, check licenses/advisories and verify hashes before load. Use safetensors where supported, restricted checkpoint loading and no `trust_remote_code` or arbitrary pickle execution. Inference must work with an empty network route, local-only loading and telemetry disabled; offline environment flags alone are not a sandbox. Use dedicated unprivileged execution, no inherited application credentials and enforced filesystem/network restrictions: the worker needs neither Walmart sessions nor YNAB tokens. Keep IPC bounded and local, with protected cache/decision journals and no raw product logs by default. An optional local process must not expose an unauthenticated LAN/public model service. Hosted Jev/OpenAI providers, automatic fallback and fine-tuning are out of scope.

Record decision source (approved mapping versus provider), selected/abstained category, model/artifact/config fingerprints and scores in the protected plan. Cache only by plan, stable product and relevant description, shortlist/descriptions and model/threshold fingerprints. Changing any of these invalidates inferred cache entries; conflicting human-approved evidence suspends reuse rather than allowing the model to overrule it. Human corrections update product mappings, not model weights. Once an allocation write begins, the frozen-plan drift rules below apply to model or shortlist changes too.

### 5. Concentrate exceptions and book all adjustments to the default

Before category allocation, require every final purchase charge to match an eligible unapproved, unsplit YNAB transaction, with positive reconciled total. Missing gift-card/unmatched payments, incomplete ledgers or any initially ineligible transaction make the order link-only at most. There is no partial-payment allocation or proportional fallback. Once application starts, recognize this plan's confirmed prior writes through the journal rather than mistaking them for preexisting user splits.

Let default-item cost be \(G\), exception-item cost be \(E\), taxes/fees/tips total be \(A\), discounts be \(D\), and final-charge total be \(T\), all represented in exact cents. Require \(T = G + E + A - D\). The default-category amount is \(B = T - E = G + A - D\). This includes item-specific as well as order-wide separately identified discounts: even an exception item's discount belongs to the default category. Exception item lines retain their known pre-discount cost. Negative default remainder, unexplained differences or unavailable pre-discount evidence prohibit allocation; do not quietly net a discount into an exception or manufacture negative/default balancing lines.

Select transactions in descending charge-amount order until their combined capacity covers all exception costs. Ties use charge date, canonical charge key and transaction ID. This gives the minimum number of exception-bearing transactions when item amounts can be divided between transactions; it is not a claim to solve whole-item bin packing or globally minimize every possible split-line arrangement. Fill selected charge capacities in that order using stable exception-item IDs, moving to the next charge only as needed. A divided item's fragments keep the same category and together equal its cost. All amounts are integer cents: no proportional weights, fractional-penny allocation or rounding redistribution is needed.

For each selected transaction, emit its exception item fragments plus one default-category remainder if positive. Omit zero lines. Use item descriptions only on exception child lines, and a concise default-category label for the remainder; do not enumerate grocery items or create tax/fee/tip/discount lines. If a transaction needs only one line, categorize it directly without a split. Nonselected transactions go entirely to the default, unsplit. If no exceptions exist, all transactions remain unsplit in the default category. Preserve every transaction total and each exception item's total, counting all spending exactly once.

**Illustrative example, not real purchase data:** Groceries $80 + household item $20 + tax $5 + fees $3 + tip $2 - discount $10 = order total $100. Walmart posts $70 and $30 final charges:

| Transaction | Exception allocation | Default Walmart Category | Result |
|---|---:|---:|---|
| $70 | $20 Household | $50 | One split transaction |
| $30 | $0 | $30 | Default category, unsplit |
| Total | $20 | $80 | All adjustments included in default |

The $70 split payload contains -20000 Household and -50000 default milliunits; the $30 transaction is -30000 in the default category without subtransactions. All remain unapproved. If one $80 exception instead belongs to a $100 order charged $70/$30, put $70 of it on the first transaction (category-only) and the remaining $10 plus $20 default on the second (split). Do not duplicate the $80 item. This is an accounting convention, not a reconstruction of Walmart's shipment/charge contents.

### 6. Review and learn entirely through YNAB

Expose `link_only` (default) and explicitly enabled `exception_first` modes alongside helper/session settings, gated by `walmart.enabled` (default `false`). These future settings replace the removed source configuration; there is no source-mode selector or retained proportional mode. Dry run shows order links, proposed categories, exception item amounts, default remainders, selected charges and skip reasons without remote writes or completion advancement. It is a diagnostic option, not a required second human-review interface.

Only initially unapproved, unsplit budget-account purchases can enter automatic category allocation. For actual splits, set parent category null and provide the child lines; for a category-only transaction, set the existing target category and omit subtransactions. Explicitly send `approved: false` for both. Preserve amount, account, date, payee, cleared state, flags, import identity and existing memo. Never unapprove already-approved transactions, delete/recreate bank transactions or send unrelated defaults. Reject reconciled/deleted parents, transfers, tracking accounts and all preexisting splits. Link-only mode does not change categories or approval.

YNAB is the review interface: the human opens an unapproved transaction, follows the order URL, compares the exception lines, adjusts categories/amounts if needed, and approves it. [YNAB's approval documentation](https://support.ynab.com/en_us/approving-and-matching-transactions-a-guide-ByYNZaQ1i) confirms unapproved transactions already affect budget balances. These are real proposed allocations in the live budget, not a separate draft or deferred spending state. Never approve automatically or reapply a proposal over human changes, even while it remains unapproved.

On later runs, read approved transaction/subtransaction state and compare it with the saved item-to-line provenance. Learn confirmed existing-category mappings only for unambiguous exception item rows, including unchanged assignments the human approved or explicit moves to the default. Rows must retain a trustworthy item association; reordered rows must not be matched by index. Merged/repurposed/deleted rows, edited allocation amounts that break provenance, uncategorized lines or conflicting fragment/product decisions do not train a mapping. Aggregate default remainders never train per-product mappings. Conflicting approved decisions suspend automatic reuse until resolved rather than letting the latest read win. Store learning per plan and stable product identity; revalidate category eligibility before reuse. Approval without a provable item row is review completion, not training evidence.

Use the documented PUT endpoint with mock-HTTP assertions against YNAB's schema, not the legacy service's PATCH assumption. A fresh read before each write detects user edits/approval; no documented compare-and-swap guarantee exists, so concurrent edits remain a risk. The documented API cannot update existing subtransactions; learning is read-only and influences future purchases, never retroactive rewrites.

### 7. Freeze the allocation and journal partial progress

Persist a protected, atomically replaced per-order plan containing canonical item/adjustment/charge fingerprints, category/default/mapping decisions, deterministic allocations and per-charge link/category/split/review status scoped to YNAB plan/account/transaction IDs. Store item-to-resulting-line provenance after read-back for learning, but no session material. Serialize local application; different machines must not operate the same scope concurrently.

Save intent before the request and completion after confirmed success. A link-only marker does not block later eligible category allocation. A category-only default write is still completed allocation, not a transaction to repeatedly recategorize because it has no subtransactions. Retry only incomplete operations with the frozen plan; reread all relevant YNAB state first. A lost/timeout response is an unknown outcome: compare remote state to saved intended categories/parent/splits. Matching state completes the journal; unchanged original state permits retry; anything else requires review. Never assume a failed response means no write.

Before any category/split write, a plan can be recomputed from fresh validated inputs. After the first allocation write, changed pricing, charge matching, default/mapping decisions or conflicting remote edits stop further automatic application for that order. A human approval can mark a confirmed operation reviewed and feed safe future learning, but never authorize replanning or overwriting other existing rows. Preserve original baselines and advance only journaled review state. Partial success is not rolled back by deleting bank transactions; YNAB provides no cross-transaction atomicity.

## Risks / Trade-offs

- **Unofficial endpoints can change or sessions can expire.** Fail closed and separate source failure from empty results; no browser or alternate-source fallback exists. Disable Walmart while recovering the helper/session. A live compatibility smoke test requires later explicit operator participation; static source review is not runtime assurance.
- **Ledger pricing may not fully reconcile real orders, especially substitutions, tips and refunds.** Start with supported USD completed purchases, retain sanitized fixtures of actual supported shapes, and link without splitting when the basis is uncertain. Do not quietly broaden monetary tolerance.
- **Exception placement does not identify actual item shipment charges.** Explain the default-and-exceptions accounting convention; do not present selected charge placement as Walmart evidence.
- **Local models can confidently misclassify items.** A small allowed list helps but does not prove accuracy. Validate exception recall, default precision and abstention on held-out Walmart fixtures, calibrate each checkpoint, retain human mappings and leave writes unapproved. Unknowns must not vanish into Groceries.
- **Small weights do not guarantee a low-memory CPU runtime.** Publish measured Laya loading/inference peaks rather than promising it fits under 1 GB. Docker Desktop/VM, JVM and helper overhead are outside that worker budget and must be disclosed separately. Fail closed if the profile cannot meet configured bounds. Docker is an optional prerequisite for model classification, not for link-only operation, and is not protection against host/daemon compromise.
- **Discounts may exceed the default item/adjustment basis.** A negative default remainder is unsupported; leave the order link-only rather than change the user's discount policy or create artificial credit lines.
- **Unapproved is not a draft.** Proposed categories immediately affect budget balances; the operator must accept that consequence when enabling exception-first writes.
- **Session files and local journals contain sensitive data.** Minimize fields and retention, restrict access and redact diagnostics; host-level compromise is outside the protections of a helper process alone.
- **YNAB has no cross-transaction atomicity or existing-split repair.** Journal partial outcomes, verify uncertain writes and stop on drift. Manual undo/review may be necessary.
